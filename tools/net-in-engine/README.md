# 把训练出的网络接进真引擎，逐档位对比

这套脚本回答的问题是：**把 `trainer/` 训出来的 `.xqnn` 当评估函数接进真引擎，
各档位的决策会不会比现在的手写评估更好？**

结论（2026-09-21 实测）：**不会**。详见 `../trainer/README.md` 与技能
`nnue-selfplay-train` 的「想把它接进引擎？先量这三个数」一节。

## 为什么需要这套脚本

「换个更准的评估函数就更强」听起来天经地义，实测不成立。要下结论必须量三件事，
而且缺一件就会得出错的答案：

| 维度 | 怎么量 | 实测结果 |
|---|---|---|
| 质量 | 同一深度下、选点不同时用固定参考（手写评估 + 深度 6）打分 | 63%~71% 的局面选点不同，但**丢分没有系统性改善** |
| 代价 | 单节点成本涨多少倍 | 手写评估 253 ns/次 → 朴素网络前向 37.3 µs/次，**整节点慢 66 倍** |
| 深度损失 | 时间预算不变时能搜多深 | **少约 1.2 层**（高级档实测只到 7 层，已经时间受限） |

## 跑法

```bash
cd tools/net-in-engine

# 1) 把 .xqnn 权重导成 JSON，并算出 Python 侧的参考输出（用于交叉验证）
python3 dump_weights.py

# 2) 给 web/js/engine.js 打补丁：产出一份「评估函数可替换」的副本
python3 patch_engine.py

# 3) 交叉验证：JS 侧的棋盘解析/特征编码/前向 必须与 Python 参考完全一致
node check.js
#    棋盘逐格、激活特征数、输出值三项都过（实测最大偏差 8.1e-5 厘兵）才能往下做

# 4) 对照实验：同深度比决策质量，再按各档位真实时间预算比深度
node exp2.js 48 with5 24        # 局面数 / 是否含深度5 / 档位对比的局面数
```

## 两个设计要点（别省）

**1. 交叉验证不能省。** 棋盘方向搞反、特征错位时，网络照样会返回一个
"看起来合理"的分 —— 只是全错。`check.js` 用 Python 的 `NumpyNet`（本来就是
"照文件格式重写一遍前向"用来校验导出的类）当参考答案。

这里运气好：`web/js/engine.js` 与 `trainer/src/xq.py` 的棋盘表示完全一致
（字符表示棋子、索引 `r*9+c`、r=0 在上），所以不需要任何坐标转换，
直接把引擎的棋盘喂给网络即可。

**2. 参考评分不要用被评估者自己。** `exp2.js` 里统一用「手写评估 + 深度 6」给
两个候选打分。这偏向手写评估，所以要意识到；**如果换个参考方向结论就翻转，
说明差异在噪声里** —— 实测就是这个情况（符号在不同档位还会翻转）。

## 补丁怎么打的

`patch_engine.py` 用**逐字替换**（不用正则、不用 sed），只改三处：

```
sign * evaluate(b)                      -> sign * (__evalFn ? __evalFn(b, side) : evaluate(b))
    evaluate: evaluate,                 -> ... 后面挂 setEval
  var api = {                           -> 前面声明 var __evalFn = null;
```

用逐字替换是因为反斜杠经工具参数传递时会被吃掉或异变（`\s` 变 `s`），
而检查脚本还会照报"替换成功" —— 这类静默失败比不检查更危险。
脚本里每处替换都断言"至少替换到 1 处"，替换完再核验新片段出现。

## 遗留问题

- iOS 侧的搜索是 Swift 实现的，这套脚本驱动的是 JS 引擎（两者算法同构）。
  Swift 的**成本**另外单独量过（见技能里的实测表）；Swift 侧的成本更高
  （手写评估只要 253 ns，而 JS 的手写评估自己就有 µs 级开销，
  所以 JS 里"只慢 10 倍"其实低估了 iOS 上的代价）
- 数据量再上一个数量级之后（唯一局面到千万级），值得重跑一次
