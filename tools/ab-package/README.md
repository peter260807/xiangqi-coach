# 象棋引擎 A/B 对局台（Windows 长跑包）

## 这是什么

用 **1200 局自对弈**比较两个引擎版本的强弱。判据是**对局胜负 + Elo 置信区间**，
不是「感觉变强了」——后者在这个项目里已经被证明会骗人（相关系数 0.98 的网络，
实际判断力还不如手写评估）。

| | 引擎文件 | 内容 |
|---|---|---|
| **A（新版）** | `web/js/engine.js` | 搜索层长将判负 → LMR 后期着法缩减 → 空着裁剪 |
| **B（基线）** | `baseline/engine.js` | 三处改动之前（= git HEAD） |

两边**同一份对局台、轮流执先、成对共用同一个起手局面**，所以差异只来自引擎本身。

## 怎么跑

**第 1 步：装 Node.js**

- 官网 <https://nodejs.org/> 下载 LTS 版，一路下一步
- **或者**用便携版：下载 `node-v22-win-x64.zip` 解压到任意目录，把该目录加进系统 PATH
- 验证：打开 cmd 敲 `node --version`，能打印出 `v22.x` 就行

**第 2 步：选一个模式双击**

```
run-ab.bat             ← 默认。A = 长将修复 + LMR + 空着裁剪（我们打算上线的配置）
run-ab.bat perp        ← A = 只带「长将修复」，剪枝强制关掉
```

**默认是 all（带剪枝）**，因为它已经有明确的实测正证据：同一个二进制、只差环境变量
的 40 局对局，**得分率 71.3%、Elo +158、区间 [+64,+251] 不含 0**，平均层数 +2.72。
这次 1200 局是它的确认。

（⚠️ 这个结论来得不容易：那版 LMR 的「缩减后重搜」用了零窗口而不是全窗口，
同一批 40 局**从 71.3% 掉到 47.5%**、区间跨 0 —— 差一点把 LMR 判成「没用」。
修好重搜那一步，收益才显出来。所以**看到「剪枝没用」时先怀疑实现，再怀疑剪枝本身**。）

`perp` 模式用来把「长将修复」单独隔离出来。它另有一批 40 局（得分率 58.8%、
8 局「长将判负」全部是新版胜），但**那批的 Elo +61、区间 [−32,+155] 跨 0** ——
40 局还不够把它钉死，所以这次 1200 局里 `perp` 模式仍然值得跑。

**第 3 步：等 8~11 小时**，窗口别关。

**第 4 步：把这两个文件发回来**

```
ab-result-all.txt       可读报告（胜和负、Elo 区间、结束原因分布）
ab-progress-all.jsonl   逐局日志（原始数据，用来复核或继续跑）
```

## ✅ 中断了可以直接续跑

**机器重启、自动更新、误关窗口 —— 都不用怕，重新双击 `run-ab.bat` 就接着跑。**

- 每局一结束就把结果**落盘并 fsync**，所以最坏情况只丢**正在进行的那一局**
- 重启后会自动认出已完成多少局，从下一局继续；最后按**全部**局汇总
  （不是只汇总本次新跑的）
- 两个模式各有自己的进度文件（`ab-progress-all.jsonl` / `ab-progress-perp.jsonl`），
  互不干扰

**保证不错位**：每局的起手局面只由「对局序号」决定（开局取用顺序 + 随机着法的种子
都只依赖它），所以续跑时的第 N 局与一次跑完时的第 N 局**是同一个局面**。
这一条是实测过的（一次跑完 vs 中断续跑，逐局比对了起手着法序列）。

**两条护栏**：

- 配置变了（每手毫秒数 / 开局数 / 随机手数 / **引擎文件**）会**拒绝续跑**并退出码 3 ——
  把两种配置的对局混在一起汇总，得到的 Elo 没有意义。日志里存了引擎文件的 sha256，
  所以「改了 engine.js 又接着跑」这种情况也会被拦住
- 最后一行写到一半（进程被强杀时必然发生）会自动跳过，不会让整个文件报废；
  中间缺局的记录也会被忽略 —— 但这种情况说明文件被动过，会明确报出来

**要丢掉进度从头跑**：`run-ab.bat --fresh`（会删掉旧的进度文件）。

## 结果怎么读

跑完文件末尾会有这么一段：

```
结果
  A 660 胜 / 120 和 / 420 负　（共 1200 局）
  A 的得分率：60.0%
  Elo 差（A - B）：+70　95% 置信区间 [+30, +112]
  独立起手局面：600 组 / 1200 局（成对设计，期望 600 组）
```

要点：

1. **看置信区间是否跨过 0**。跨过 0（比如 `[-8, +60]`）就是「这批看不出差别」，
   照实说无差别，**不要**把 +26 当成「涨了 26」。
2. **「独立起手局面」这一行必须等于局数的一半**。不等于就说明有不同对撞了同一局面，
   名义局数被注水 —— **统计分辨力按独立局面数算，不按局数**。这次已设
   `--random-plies 4` 保证每对起手局面都不同。
3. **结束原因分布也要看**：`perp` 模式下如果「长将判负」的局数明显下降，说明修复在起作用；
   `all` 模式下这类局数应当**接近 0**（搜索层已经不会主动走进去）。
4. 分辨力：1200 局（600 组独立局面）大致能分辨 **±30 Elo** 量级的变化。

## 目录里都有什么

```
run-ab.bat                一键脚本（纯 ASCII + CRLF，cmd 下不会乱码）
ab-result-all.txt         跑完才有（perp 模式是 ab-result-perp.txt）
ab-progress-all.jsonl     逐局日志 / 断点续跑用（perp 模式是 -perp.jsonl）
tools/match.js            对局台
tools/lib/uci-engine.js   UCI 适配（本包用不到，但 match.js 会 require）
web/js/engine.js          A 版引擎（剪枝默认**开**，可用环境变量关）：
                            XQ_NO_LMR=1 / XQ_NO_NULL=1   关掉 LMR / 空着裁剪
                            XQ_LMR=1 / XQ_NULL=1         显式打开（默认就是开）
                            XQ_NO_PERPETUAL=1            关掉长将判负（归因用）
                          run-ab.bat 的两个模式就是靠这组变量切的，不用改代码
web/js/library.js         开局库
web/js/library-data.js    开局库数据（8 组棋路）
baseline/engine.js        B 版引擎
results/                  历次 A/B 留档（含那次把剪枝判错的、以及修正后的两批）：
                            2026-09-23-ab-perpetual-40games.txt        长将修复  58.8% / +61 [−32,+155]
                            2026-09-23-ab-prune-BUGGY-...-40games.txt  剪枝(有 bug) 47.5% / −17
                            2026-09-23-ab-prune-fixed-40games.txt      剪枝(已修)  71.3% / +158 [+64,+251]
README.md                 本文件
```

## 想自己改参数

编辑 `run-ab.bat` 顶部的变量：

```bat
set GAMES=1200          :: 局数。分辨力大致按 1/sqrt(局数) 变好。必须偶数
set MS=300              :: 每手思考毫秒数
set OPENINGS=8          :: 用几个开局（库里一共就 8 个）
set OPENPLIES=8         :: 每个开局先摆几手（8 手才能把 8 组完全分开）
set RANDOMPLIES=4       :: 开局之后再走几手随机着法 —— 见下
```

**`RANDOMPLIES` 别改成 0。** 开局库只有 8 组棋路，不随机的话一对里的两局共用同一开局，
**实际不同的棋只有 16 盘**，跑 1200 局等于把同一盘重放 75 遍 —— 样本量是假的。
对局台会在开跑前和结束时各告警一次，但如果只看到最终的胜负数字，很容易被它骗过去。

**`GAMES` 一定要偶数**，否则两边执先次数不等。

## 一个要事先知道的局限

**Windows 上没有 Swift 编译器**，所以这个包比的是两版 **JS** 引擎。
iOS 用的 Swift 引擎是同一套算法的另一份实现（同 300ms 下比 JS 版深约 1 层），
但**两者的改动是逐行同构的**，所以这里测出的「相对强弱方向」可以直接外推到 iOS；
绝对 Elo 数不要直接搬到 App 上。
