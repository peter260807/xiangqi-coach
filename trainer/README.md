# 象棋 NNUE 训练包

用 Pikafish 的自对弈数据，训练一个**轻量的局面评估网络**，最终导出一个可以被引擎加载的网络文件。

一句话理解它在做什么：**让一个小网络去学会模仿 Pikafish 的判断**。
学成之后，把它接到自己的搜索引擎里，棋力就会明显强于手写的评估函数。

---

## 一、跑之前要准备两样东西

### 1. Python 3.10 或更高

下载：https://www.python.org/downloads/

安装时**务必勾选 "Add python.exe to PATH"**，否则命令行里找不到 `python` 命令。

### 2. Pikafish 引擎 + 神经网络权重

1. 打开 https://github.com/official-pikafish/Pikafish/releases
2. 下载最新那个 `Pikafish.YYYY-MM-DD.7z`（约 51 MB）
3. 解压，把下面两类文件复制到本目录的 `engine\` 文件夹：

| 包里的文件 | 放到哪里 | 说明 |
|---|---|---|
| `Pikafish-Windows-x86-64-universal.exe` | `engine\pikafish.exe` | 建议改名，方便脚本识别 |
| `pikafish.nnue` | `engine\pikafish.nnue` | 约 50 MB，**必须和 exe 放同一目录** |

**放进去就行，不需要改任何配置。** 脚本会自己在这个目录里找，也允许你解压时
多套了一层目录。万一找不到，它会把该目录的实际内容列出来给你看。

> ⚠️ 注意从官方仓库 `official-pikafish/Pikafish` 下载。网上有不少仿冒站，
> 同一件事一会儿说基于 NNUE 一会儿说基于 MCTS，协议和版本号还互相矛盾。

## 二、怎么跑

> 📌 **脚本界面是英文的**（比如 `Step 3/5 - Generate training data`），这是刻意的。
>
> `.bat` 文件在中文 Windows 上会被 cmd 按 **GBK(936)** 解码。如果里面写中文，
> 而文件是 UTF-8 编码，轻则显示乱码，**重则因为乱码字节里出现特殊字符导致
> 脚本直接跑不起来**。注意 `chcp 65001` 救不了这个 —— 它只改控制台的**输出**，
> 不改 cmd **读取文件**用的编码。
>
> 所以约定是：**bat 只负责干活（纯英文），中文说明都写在本文档里，
> 而 Python 脚本输出的中文是正常的**（bat 里设了 `PYTHONIOENCODING=utf-8`）。

### 方式 A：分步跑（推荐第一次用）

按顺序双击，每步都有输出可以看：

| 脚本 | 做什么 | 大致耗时 |
|---|---|---|
| `win\1-install.bat` | 装 numpy 和 PyTorch **CUDA 版**（约 2.5 GB，走 PyTorch 官方索引） | 10~30 分钟（看网速） |
| `win\2-selfcheck.bat` | 环境自检，确认引擎和显卡都能用 | 10 秒 |
| `win\0-fix-torch.bat` | **只在 PyTorch 有问题时用**：自动区分「装错包 / 驱动太旧 / c10.dll 报错」并修复 | 5~15 分钟 |
| `win\3-gen-data.bat` | 生成训练数据 | **2~4 小时** |
| `win\4-train.bat` | 训练网络 | **1~3 小时** |
| `win\5-export-verify.bat` | 导出 + 验证效果 | 1~2 分钟 |

### 方式 B：无人值守

确认 `1-install.bat` 和 `2-selfcheck.bat` 都通过之后，直接双击 `win\run-all.bat`，
它会自动依次跑完数据生成 → 训练 → 导出验证。可以出门前点开，回来直接看结果。

## 三、参数怎么调

三个 `.bat` 文件的开头都有参数区，用记事本打开就能改。

### 数据生成（`3-gen-data.bat`）

```bat
set WORKERS=14      :: 并行进程数。5700X 是 8核16线程，14 比较合适
set DEPTH=8         :: 每步搜索深度。调大质量更高但更慢
set MINUTES=180     :: 跑多少分钟
```

**关于 DEPTH**（对最终效果影响最大的一个）：

| DEPTH | 相对速度 | 数据质量 | 建议 |
|---|---|---|---|
| 6 | 最快 | 一般 | 只想先跑通流程看看 |
| **8** | 基准 | 好 | **推荐起手** |
| 10 | 约慢一半 | 更好 | 时间充裕时用 |
| 12 | 约慢 4 倍 | 最好 | 数据量少时用来提质 |

> 有个坑要提醒：**别用 `movetime` 来限流**。它会让引擎把时间用满，
> 哪怕 2ms 就找到最优着法了。实测下同样的局面，
> `movetime 50` 测出来 20 局面/秒，`depth 8` 能到 468 局面/秒 —— **差 20 倍**。
> 这个包已经统一用 `depth`，不用你操心。

### 训练（`4-train.bat`）

```bat
set EPOCHS=8        :: 把数据过几遍
set BATCH=8192      :: 每批样本数。显存需求约 0.4 GB，8G 的卡也毫不吃力
set LR=0.001        :: 学习率
```

数据多的时候，`EPOCHS` 可以适当调小；数据少就调大。

### 换显卡了，参数要改吗

**基本不用改。** 这个项目对显卡要求很低，中端卡都能跑顺：

| | RTX 2080Ti | RTX 3060Ti |
|---|---|---|
| 架构 / 计算能力 | Turing / sm_75 | Ampere / sm_86 |
| FP32 算力 | 13.45 TFLOPS | **16.2 TFLOPS**（高 20%） |
| 显存 | 11 GB | 8 GB |
| 显存带宽 | 616 GB/s | 448 GB/s（低 27%） |
| CUDA 版本 | cu126 起 | cu126 起（同样支持） |

**为什么换卡几乎没感觉** —— 实测把训练的一步拆开（batch 8192）：

| 环节 | 占比 |
|---|---|
| CPU 侧：特征编码 + 取数 + 张量转换 | **约 35~40%** |
| GPU 侧：前向 + 反向 | 约 60~65% |

看着 GPU 占大头，但这个网络**只有 68 万参数**（1260→512→64→1），对任何现代显卡都是小活。
真正决定吞吐的是 CPU 侧的特征编码和每批数据的搬运。于是：

- **数据生成阶段完全由 CPU 决定**，显卡一点忙都帮不上
  （Pikafish 官方 FAQ 明确写着不支持 GPU 推理）
- **训练阶段**两张卡的实际差距远小于纸面的 20%，因为瓶颈不在算力

### Mac 上别用 MPS，直接用 CPU

在 M1 Pro（10 核）上实测过两种后端，结论反直觉但很干脆 —— **CPU 比 MPS 快 5 倍**：

| 后端 | 整步吞吐 | 每条样本耗时 |
|---|---|---|
| CPU | **24.5 万局面/秒** | 4.1 µs |
| MPS（`--device mps`） | 4.9 万局面/秒 | 20.4 µs |

原因不在矩阵乘 —— 单看矩阵乘 MPS 反而更快（1.75 ms vs Python CPU 的 2.43 ms）。
瓶颈在第一层的**稀疏 gather / scatter**（也就是 EmbeddingBag 的反向）：
MPS 上它每条样本固定花 20.4 µs，而且**和批大小完全无关**（B 从 256 到 8192
都是这个数），说明是吞吐差不是启动开销。
整张网才 68 万参数，CPU 完全喂得动，所以 `pick_device()` 在 Apple Silicon 上
直接返回 CPU。想自己复核：`--device mps` 跑一遍，和 `--device cpu` 对比。

**显存 8G 够不够？够，而且很宽裕。** 实测 batch 8192 的全部张量：

| 组成 | 占用 |
|---|---|
| 特征索引 (8192, 32) int64 | 2 MB |
| 各层激活 | 19 MB |
| 反向再存约两倍中间量 | 38 MB |
| PyTorch 运行时本身 | 约 300 MB |
| **合计** | **约 350 MB** |

8 GB 有 **20 倍以上裕度**，`BATCH` 不用调小。`2-selfcheck.bat` 会把你机器上的
实际显存和结论直接打出来，不用自己算。

**内存才是提升空间。** 数据集是**全量读进内存**的（1 亿局面约 9.3 GB），
内存宽裕就可以把 `MINUTES` 延长、生成更多数据 —— **数据量对最终效果的影响
远大于显卡**。

> 顺带一提：拼接分片时峰值内存约为数据量的两倍，所以 24 GB 以上比较稳妥。
> 自检里会一并报出来。

### 无人值守（`run-all.bat`）

参数分两段，一段管数据生成、一段管训练，含义相同。
默认配置按 8 核 16 线程 CPU 估算约 **5~8 小时** —— 显卡强弱对这个时长影响很小。

## 四、产出什么

跑完之后 `logs\` 目录里会有：

| 文件 | 是什么 |
|---|---|
| **`xq-v2.xqnn`** | **最终网络**（约 2.7 MB），引擎加载这个 |
| `weights.pt` | PyTorch 权重，可以继续训练 |
| `train.log` | 训练日志 |
| `data\part_*.bin` | 训练数据，确认没问题后可以删掉腾空间 |

### 网络文件格式

`xq-v2.xqnn` 是个简单的二进制文件（全部 little-endian）：

```
偏移   类型              内容
0      char[4]           魔数 "XQNN"
4      uint32            格式版本（2）
8      uint32            特征维度 feat_dim（1260）
12     uint32            第一层宽度 l1（512）
16     uint32            第二层宽度 l2（64）
20     uint32            output_scale：输出 1.0 对应多少分（100）
24     float32[l1][feat_dim]   第一层权重
...    float32[2][l1]          先后手偏置
...    float32[l2][l1]         第二层权重
...    float32[l2]             第二层偏置
...    float32[1][l2]          第三层权重
...    float32[1]              第三层偏置
```

> **v1 → v2 是破坏性变更。** v1 的网络输出经过 sigmoid，含义是「走子方胜率」；
> v2 去掉了 sigmoid，输出**直接就是分值**（单位由 `output_scale` 给出）。
> v1 里偏移 20 是保留位（写 0），v2 才开始有含义。加载方必须按版本号分支 ——
> 混用会得到一个看上去正常、实际上毫无意义的数。`export.py` 里的
> `NumpyNet` 同时支持两个版本，就是为了让新旧模型能放在一起做对比评估。

引擎侧照着这个写推理就行：

```
acc[i] = Σ feat_weight[i][f] + side_bias[side][i]   // f 是该局面的激活特征
h1[i]  = clamp(acc[i], 0, 1)
h2[j]  = clamp(Σ fc2_weight[j][i] * h1[i] + fc2_bias[j], 0, 1)
value  = Σ fc3_weight[0][j] * h2[j] + fc3_bias[0]
cp     = value * output_scale                        // 走子方视角的分差
```

想显示胜率的话在展示层再套一次 `sigmoid(cp / 400)`，**不要放进网络里** ——
那层压缩正是 v1 排序能力失效的原因（见第五节）。

第一层是个累加器，所以引擎侧可以做**增量更新**：一步棋只影响两个格子
（起点清掉、终点加上），把对应两行权重加减一下就行，不必每次重算 1260 维。

**特征怎么编码**（这一步必须两端一致，否则网络等于废的）：

- 棋盘按 `r * 9 + c` 编号，`r=0` 是黑方底线（对应 UCI 的行 9），`r=9` 是红方底线
- 每个有子的格子产生一个特征，索引 = `格子编号 * 14 + 类型编号`
- 类型编号**跟走子方有关**：轮到谁走，谁的子就是 `0-6`（帅仕相马车炮兵），对方是 `7-13`
- 一共 `90 * 14 = 1260` 维

视角归一化这一步很关键：轮红方走和轮黑方走，同一个棋盘的编码是不同的。
这样网络只需要学一套「己方 / 对方」的概念，不必为红黑各学一套，样本效率翻倍。

## 五、怎么看结果

`5-export-verify.bat` 最后会打出一份验证报告，重点看这两个数：

```
  均势档相关系数       : 0.5275   （|cp|<100，170094 个局面 —— 这一项才是关键）
  换算成引擎分值：平均偏差 46.3 分（均势档 25.6 分）
```

### 相关系数会骗人，有两层原因

**第一层：整体相关系数被少量极端局面撑高。**
它是全样本算的，而大分差局面（一方大优、分值跨度上千）会把整体数字拉上去。
v1 的日志报 **0.9797**，看着几乎完美，但分档看完全是另一回事：

| 局面类型 | 相关系数 | 平均偏差 |
|---|---|---|
| 均势（绝对值小于 50，占一半以上） | **0.62** | 0.008 |
| 稍优 50~200 | 0.92 | 0.016 |
| 明显优势 200~800 | 0.99 | 0.015 |
| 大优 / 杀棋 800 以上 | 0.99 | 0.021 |

所以 `verify.py` 现在**单独把均势档的相关系数列出来**，那一项才反映真实水平。

**第二层（更阴险）：验证集泄漏。** v1 是按「记录」随机切训练/验证的，
但同一局面在一局棋里会反复出现、在不同对局里也会撞上 ——
于是同一局面的"另一个副本"就躺在训练集里，**网络在考自己做过的题**。

v2 改成按 `(棋盘, 走子方)` 的哈希去重并划分，顺手量出了真实重复率：

```
3017 万条记录  ->  只有 472 万个唯一局面（重复率 84.3%）
```

**"3017 万局面"实际上是 472 万，平均每个局面被记了 6.4 次。**
后果有两层：验证指标虚高；训练时六成算力花在重复样本上，
还反复给「开局附近那几十种走法」偷偷加权重。

### 判断力测试（比相关系数重要）

`verify.py` 只测「分数拟合得像不像」，不测「能不能挑对棋」——这两件事**不是一回事**。
想知道网络能不能当评估函数用，跑：

```bat
python tests/eval_net_strength.py --positions 150 --depth 10 --dump positions.json
node tests/eval_handcrafted.js positions.json
```

做法是：给一批局面，让引擎用 MultiPV 排出 8 个候选着法（引擎已排好序），
再看网络挑中的那一步排在引擎的第几位。`--dump` 出来的 JSON 可以交给
`eval_handcrafted.js`，让 `web/js/engine.js` 里那套手写评估做**同场对照**。

输出里几个数字**必须放在一起看**：

| 对照 | 含义 |
|---|---|
| 引擎 depth 1 | 同样只做浅层评估的参照 |
| 手写评估（位置价值表） | 网络要替代的就是它。两个都是静态评估，比出来才算数 |
| 随机瞎猜 | 基准线（8 个候选时是 4.50） |

144 个局面、每局 8 个候选、标准答案取引擎 depth 10 的排序。
下面四组网络是**在同一批局面、同一组候选**上跑出来的，可以互相比较：

| 评估方式 | 平均名次 | 平均丢分 | 选中首选 |
|---|---|---|---|
| 引擎只搜 depth 1 | **0.60** | **6.5 分** | 62.5% |
| 手写评估（位置价值表） | 2.63 | 53.8 分 | 24.3% |
| NNUE v1（胜率目标，256/32） | 2.74 | 53.0 分 | 24.3% |
| NNUE c256（线性目标，256/32） | 2.85 | 53.0 分 | 22.9% |
| NNUE c512（线性目标，512/64） | 2.82 | 78.3 分 | 22.9% |
| NNUE d512（**改用高多样性数据**） | **2.69** | **50.1 分** | 22.2% |
| 随机瞎猜 | 4.50 | — | 12.5% |

**「平均丢分」比「平均名次」灵敏得多，应该优先看它。** 名次是 0~7 的整数，
144 个局面下均值的标准误就有约 **0.24** —— 上面四组网络的名次差只有 0.05~0.16，
**全部落在噪声里**（两两配对 t 检验的 p 值都在 0.18 以上，符号检验也是 40 多比 40 多）。
丢分是连续量，同样的样本量下能把差别放大出来，而且它才是真正在乎的东西：
换这个评估函数要付出多少棋力。

### 数据多样性：重复率从 84.3% 压到 32.8%

调大 `--opening-plies`（6 → 14）之后重新生成一批数据对比：

| | 旧 | 新 |
|---|---|---|
| 记录数 | 3017 万 | 335 万 |
| **唯一局面** | **472 万** | **225 万** |
| **重复率** | **84.3%** | **32.8%** |

新数据**记录数只有旧的九分之一，唯一局面还少一半**，但训出来的 d512
在两个指标上都拿到了四组里最好的成绩（名次 2.69、丢分 50.1，都优于手写评估）。

> ⚠️ 但**别急着下"多样性一定赢"的结论**：差异仍然不显著
> （d512 vs 手写评估 丢分 p=0.57、名次 p=0.79）。144 个局面太小了，
> 要真正分辨这些差别，评测集得扩到 **500 个局面以上**。
> 现在能确定的是两件事：**重复率这个工程指标被实打实地修好了**，
> 以及**"堆记录数"没用**（旧数据 9 倍的记录数换来的是更差的结果）。

### 别用平均值下结论，做配对检验

网络 2.82 vs 手写 2.63，看着像"网络更差"。`eval_handcrafted.js` 会直接给出
配对 t 检验和符号检验（后者不依赖分布假设）：

```
平均名次差    : 0.188（标准差 2.947）
配对 t 检验   : t = 0.763，双侧 p = 0.445
符号检验      : 网络更好 49 局 / 手写更好 50 局，双侧 p = 1.000
```

**p = 0.445，差异不显著。** 正确结论是"**网络没有超过手写评估**"，
而不是"网络更差"。49:50 几乎是完美对半 —— 两者水平真的相当。

> ⚠️ 手写评估的名次会随基准深度变（候选集不同），所以跨次运行比较
> "2.44 vs 2.63"没有意义。**只有同一批局面、同一组候选、同一次运行里的
> 数字才能互相比较。**

### 先确认基准本身有没有分辨力

在讨论"网络行不行"之前，先量候选着法之间到底差多少分。实测同一批 144 个局面：

| 统计量 | 数值 |
|---|---|
| 第 2 名只比首选差（中位） | **4 分** |
| 第 8 名只比首选差（中位） | **54 分** |
| 8 个候选全挤在 20 分以内的局面 | **34%** |
| 8 个候选全挤在 50 分以内的局面 | **49%** |

而网络的均势局误差是 **25.6 分**。三分之一的局面里，
8 个候选的整个跨度还不到网络误差的量级 —— **那里的"排序"本身就落在
引擎自己的搜索误差里，任何评估函数都不可能排对。**

按跨度分层再看（同一批局面）：

| 子集 | 局面数 | 手写 | 网络 | 引擎 depth 1 |
|---|---|---|---|---|
| 全部 | 144 | 2.63 | 2.82 | 0.60 |
| 跨度 <20 分（纯噪声） | 49 | 2.80 | 2.80 | 0.84 |
| 跨度 20~100 分 | 47 | 2.34 | 2.55 | 0.47 |

**所以"平均名次 2.8"这个数字不能单独解读**，必须同时说明候选的差距分布。

### v2 改了四处

| 改动 | 原因 |
|---|---|
| **训练目标换成线性分值**：直接回归 cp（单位取「兵」，`OUTPUT_SCALE=100`），损失用 Huber | 去掉 sigmoid 的饱和区，优化问题好得多（见下表）；Huber 把单样本梯度封顶，1.13% 的杀棋局面（±3000 分）不会靠"误差大"把梯度全抢走 |
| **按局面去重 + 按局面哈希划分训练/验证** | 重复率 84.3%（见上）。不去重等于六成算力花在重复样本上；按记录随机切还会泄漏 |
| **网络放大到 512/64**（68 万参数） | v1 只有 32 万参数 |
| **`--opening-plies` 默认 6 → 12** | 开局随机步数太少会让后续着法完全由引擎决定，是重复率高的源头 |

训练目标的改动**让优化问题变得好得多**，这是可以量化的：

| | v1（sigmoid + BCE） | v2（线性 + Huber） |
|---|---|---|
| loss | 0.6557 → **0.6532（第 2 轮就卡住）** | 0.838 → **0.492（第 8 轮仍在降）** |
| 相对"永远输出常数"的基准 0.6931 | 只解释掉 **6%** 信息量 | 口径不同，不可直接比 |
| 均势档相关系数 | 0.62（**但验证集泄漏，偏乐观**） | 0.5275（无泄漏） |
| 均势档平均偏差 | — | 25.6 分 |
| 训练耗时（M1 Pro CPU） | — | 2.6 分钟（256/32）/ 3.6 分钟（512/64） |

### ⚠️ 被实验推翻的假设：换训练目标并没有改善排序

这一条值得单独写出来，因为**推理很顺、结果是错的**，很容易重走。

**曾经的理论**：候选之间差距中位只有 3~4 分，而 `sigmoid(cp/400)` 把它压成
0.0019 的胜率差，网络输出误差却是 0.0121 —— 信噪比 0.16，
是压缩损失了分辨率。推理看上去无懈可击。

**实验**：同一份数据、同一套去重与划分，只换训练目标，并跑两组网络尺寸隔离变量：

| 组 | 训练目标 | 网络 | 平均名次 |
|---|---|---|---|
| A（v1） | sigmoid 压缩 + BCE | 256/32 | 2.74 |
| C | 线性分值 + Huber | 256/32 | 2.85 |
| B | 线性分值 + Huber | 512/64 | 2.82 |
| — | 手写评估（同一批局面） | — | 2.63 |

**三组网络互相之间统计上不可区分，也都没超过手写评估。**
换目标 + 放大网络 + 去重，一个都没能把判断力推上去。

**推理错在哪**：它混淆了「输出的数值刻度」和「评估函数的知识分辨率」。
去掉 sigmoid 确实让数值刻度变成线性的，但网络的**判断误差（均势局 25.6 分）
并没有变小**。排序需要的不是"刻度更细"，而是"误差更小"。

也排除过"实现有 bug"这个可能：`xq.feature_indices` 与 `train.compute_features`
是两套独立实现，抽查 219 个局面**结果完全一致**，评估链路是好的。

### 下一步该动哪里

**优先级从高到低（按这次实验的结论排）：**

1. **数据：先量重复率 → 去重 → 提高开局多样性 → 最后才是堆量。**
   实测调大 `--opening-plies` 把重复率从 84.3% 压到 32.8% 是**确定有效**的；
   而"多跑 9 倍的记录数"反而训出更差的网络。
   量级上还差得远（225 万唯一局面 vs 专业 NNUE 的几十亿），
   但在那个量级之前，**先保证每一局都不重复**比堆时长划算得多
2. **基准：先扩到 500 个局面以上，并且优先看「平均丢分」。**
   144 个局面连 0.16 的名次差都分辨不出来，继续在这个尺度上比就是自欺欺人。
   另外要对候选差距做分层：34% 的局面里 8 个候选全挤在 20 分内，
   那些局面的"排序"落在引擎自己的搜索误差里，谁排都是随机的
3. **网络容量。** 只有数据量够了、训练 loss 明显还没收敛时再动
4. ~~换训练目标~~ —— **已实验证伪，它不是解药**

### 还有一条更根本的：静态评估本来就追不上浅层搜索

同一批局面下，**引擎只搜 depth 1 的平均丢分是 6.5 分，而所有静态评估
（手写的和网络的）都在 50 分上下**，差距近 8 倍。
depth 1 只比静态评估多做一件事：**走一步看看对方能吃什么**。

这说明真正的差距不在"评估函数学得像不像"，而在**没有搜索**。
想让它真正能用，方向是把网络接进带搜索的引擎里（见 `docs/nnue-vs-llm.md`），
而不是继续在静态评估上抠那几个百分点。

想复现 v1 的旧行为做对照：

```bat
python src\train.py --data data --out logs\old --target-mode winrate --no-dedup --l1 256 --l2 32
```

想复现高多样性那组（需要先重新生成数据）：

```bat
python src\gen_data.py --workers 8 --depth 8 --opening-plies 14 --minutes 30 --out data\v2
python src\train.py --data data\v2 --out logs\d512 --l1 512 --l2 64
```

## 六、常见问题

**Q：说找不到引擎，但我明明放进去了**

脚本会把你 `engine` 目录里**实际看到的内容**列出来，先对着那个清单排查：

1. **位置对不对** —— 应该是 `trainer/engine/`，不是 `trainer/` 根目录，
   也不是 `win/engine/`
2. **exe 和 `.nnue` 是不是同一层** —— 引擎只会去 exe 旁边找权重
3. **是不是解压多套了几层目录** —— 多套一层也能找到，套两层以上就不行了

实在理不清，直接用完整路径绕开自动查找：

```bat
python src/gen_data.py --engine "D:/pikafish/pikafish.exe" --out data
```

**Q：双击 bat 一闪就没了，看不到报错**

在 `trainer` 目录里开一个 cmd，直接敲 bat 的名字（不要双击）：

```bat
cd /d 你的 trainer 目录
win\3-gen-data.bat
```

窗口会停住，报错也就留在屏幕上了。或者绕开 bat 直接跑 Python，
参数和 bat 里完全一样：

```bat
python src/gen_data.py --workers 14 --depth 8 --minutes 180 --out data
```

**Q：引擎启动失败 / 权重加载不了**
多半是 exe 和 nnue 版本不匹配。用同一个发布包里的这两个文件，
别把不同版本混着用。可以在命令行手动跑一次 exe，它会打印具体原因。

**Q：`torch\lib\c10.dll` 初始化失败（WinError 1114）**

这是 Windows 上最常见的 PyTorch 问题。按可能性从高到低：

1. **PyTorch 2.9.x 本身有这个 bug** —— 多人反馈回退到 2.8.0 就好了。
   `1-install.bat` 已经锁定 2.8.0；如果你之前手动装过别的版本，
   跑一次 `0-fix-torch.bat` 会自动处理。
2. **缺少 Visual C++ 运行库** —— 下载安装（注意要 x64 那个）：
   https://aka.ms/vs/17/release/vc_redist.x64.exe
   装完**重启电脑**再试。
3. **装了 CUDA 版但机器环境不匹配** —— 可以先装 CPU 版把整个流程跑通，
   确认脚本没问题了再换 CUDA 版。

`0-fix-torch.bat` 会按这个顺序自动排查一遍，不用手工折腾。

**Q：自检说装的是 CPU 版 PyTorch / CUDA 不可用** ⚠️ 最容易踩的坑

**PyPI 上 Windows 的 torch 轮子是纯 CPU 版**（230 MB；同版本 Linux 轮子 847 MB
才含 CUDA）。所以 `pip install torch` 会**安装成功、看起来一切正常，但显卡永远用不上**，
`torch.cuda.is_available()` 一直是 `False`——不报错，只是慢。

必须指定 PyTorch 自己的索引：

```
pip uninstall -y torch
pip install "torch==2.8.0" --index-url https://download.pytorch.org/whl/cu126
```

⚠️ 那句 `uninstall` 不能省。已装的 CPU 版版本号就是 `2.8.0`，pip 认为
`torch==2.8.0` 已经满足，**不会重新下载**，你会一直停在 CPU 版上。

怎么判断是哪种情况，看自检输出里的「CUDA 标记」：

| 自检显示 | 含义 | 怎么办 |
|---|---|---|
| `CUDA 标记：无` | 装的是 CPU 版，与驱动无关 | 按上面两条命令重装 |
| `CUDA 标记：12.6` 但仍不可用 | 包对了，**驱动太旧** | `nvidia-smi` 看版本，低于 527 就去 nvidia.com 更新驱动 |

CUDA 版本与驱动的最低要求：`cu126` 要 527+，`cu128` 要 570+，`cu129` 要 575+。
2080Ti 是 Turing（sm_75），这三个都还支持。想换版本就打开 `win\1-install.bat`
改 `CUDA_INDEX` 那一行。

**Q：磁盘不够**
1 亿个局面约占 9.3 GB。跑之前留 30 GB 比较稳妥。
数据用完（训练结束后）可以删掉 `data\` 腾空间。

**Q：训练到一半想停**
按 Ctrl+C 就行，每轮结束都会存 checkpoint，已训练的进度不会丢。
想接着训就把 `EPOCHS` 调大重跑，它会从头开始 —— 如果要严格续训，
需要改 `train.py` 加加载 checkpoint 的逻辑。

**Q：数据生成阶段某个 worker 报"引擎异常，重启"**
不影响，脚本会自动重启那个 worker 继续跑，最后会统计异常次数。
偶尔一两次正常，如果频繁出现就要检查机器是不是过热或内存不足。
