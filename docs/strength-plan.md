# 提升棋力：实测基线与路线规划

> 本文数字全部为**本机实测**：Apple M1 Pro、Swift 引擎 **Release 档**（`-O -whole-module-optimization`）、
> 单线程。测量台 `tools/search-bench/`，一条命令复现：`./tools/search-bench/run.sh`。
> 评测日期：2026-09-22。
>
> 为什么必须用 Release 档测：Swift 的 `-Onone`（模拟器 Debug 档）在数组密集的代码上会慢好几倍，
> 拿它规划会严重低估真机上到底能搜多深。`run.sh` 默认两档都跑。

---

## 结论速览

1. **难度档的「深度」标签有一半是假的。** 开局阶段 `高级(8层/3.5s)` 与 `大师(12层/6s)`
   **都只搜到 7 层**，第 7 层都是**搜完**的，而且**实测返回同一手棋**（两者都是 `炮八平七`）。
   用户点「大师」等 6 秒，拿到的是「高级」的结果。实际梯度因此只有四档：
   入门 1 层 / 初级 3 层 / 中级 5 层 / **高级 7 层 = 大师 7 层**。
2. **开局是效率重灾区。** 同样 32 个棋子，开局搜满 8 层要 **2833 万节点**，
   中局只要 **343 万** —— 差 **8.3 倍**。不是子力多，是**着法排序在开局失效**。
3. **评估不是杠杆，搜索是**（本轮再次印证）。静态评估 0.24 µs/次，但判 100 个局面只有 0.53 的
   分辨力；而每多搜一层就多一层实打实的战术。往搜索里塞东西（更贵的评估）只会让深度变浅 ——
   这一点 9-21 已经实测过（网络慢 66 倍，同样时间少搜 1.2 层，质量并列）。

## 一、基线

### 1.1 微观成本（中局局面，39 个着法，5000 次取均值）

| 操作 | 单次成本 | 说明 |
|---|---|---|
| `genMoves`（全量伪合法） | **0.29 µs** | 一次吐出 39 个着法 |
| `legalMoves`（逐着试走 + 被将检测） | **5.58 µs** | 39 个着法逐个 make/unmake + `inCheck` |
| ↳ 折算到每个着法的合法性检查 | 0.14 µs | 也就是每个节点光「排掉非法着法」就要 ~5.5 µs |
| `evaluate`（静态评估） | **0.24 µs** | 全盘 90 格扫一遍 |
| `inCheck`（被将检测） | 0.08 µs | |

> 测量陷阱（已踩）：写成 `_ = Rules.inCheck(b, side)` 时，`-O` 会把整个调用**提出循环**
> （纯函数 + 结果无人使用），量出 0.06 µs 这种不可能的假数字。测量台里的每次调用都必须
> 把结果喂进一个 `@inline(never)` 函数里的全局变量，并打印校验和自证循环没被优化掉。

- 引擎真实速度 **2500–3900 千节点/秒**（M1 Pro 单线程）。

## 二、为什么「开局更难搜」是个可下手的信号

同样 32 个棋子，开局 8 层 2833 万节点，中局 8 层 343 万节点。差在哪？

**不是子力，是排序。** 开局局面高度对称、子力均衡，静态评估给出的分数**大量并列**；
置换表里也没有可复用的深层结论。于是：

- **杀手着法**：开局几乎没有「某个着法在同一层反复造成截断」的稳定模式
- **历史启发式**：分数并列 → 历史表积累不起区分度 → 排序退化成近似随机
- **alpha-beta 的剪枝率直接取决于排序质量**，排序退化就等于退化成近乎全搜

中局/残局有明确的好坏着（该吃子了、该逃车了），排序有信息量，于是同深度省下 8 倍节点。

**这是本次最值钱的一条**：优化目标不再是笼统的「让引擎变强」，
而是**「把开局的节点数降一个数量级」**——有明确指标、明确场景、明确验收。

### 2.1 先把一个「看着矛盾」的旧结论说清

README 里有一组实测（`tools/pk-match.js`，JS 引擎 vs Pikafish，见 README「和 Pikafish 对局」一节）：
把 Pikafish 压到**固定 2 层**，让它比本项目引擎少搜近 3 倍深度，它仍然 **0 胜 3 负 1 和**。
README 据此写的是「**差距不在搜索深度，而在评估函数**」。

这和本文「评估不是杠杆」看着打架，其实在说两件不同的事：

| 说法 | 比较对象 | 成立吗 |
|---|---|---|
| 「差距在评估函数」 | **我们 vs Pikafish** | ✅ 成立。同深度下 Pikafish 的 NNUE 评估远强于我们的手写评估，这一段差距真实且巨大 |
| 「评估不是杠杆」 | **我们 vs 我们的下一步** | ✅ 也成立。在「子力 + 位置表」这个**特征族内**，数据量 / 网络容量 / 训练目标 / 将位条件四条全部实测为无效（见第四节） |

合起来读：**到 Pikafish 的差距里确实有一段是评估段的，但我们在评估这一侧已经挖不出东西了**
—— 除非换特征族（`FullThreats`，见 P5），那是大工程；
而**搜索这一侧从来没优化过**，本次实测还给出了明确的 10 倍量级空间。

两者不冲突：一个说「天花板在哪」，一个说「下一步先迈哪只脚」。

## 三、方案清单（按 ROI 排序）

### P0 — 先补上「能测棋力」这件事（前置，不做则后面全是感觉）✅ **已完成（2026-09-22）**

**问题**：App 里真正在用的 **Swift 引擎完全没法测棋力**。`tools/pk-match.js`
驱动的还是 `web/js/engine.js`（JS 版），Swift 版没有任何对外对局接口。
后果就是 9-22 之前那种局面：改完只能说「感觉变强了」「看着没报错」。

**做出来的东西**：

| 文件 | 是什么 |
|---|---|
| `tools/uci/main.swift` + `run.sh` | 把**同一个** Swift 引擎包成标准 UCI 子进程（`uci`/`isready`/`ucinewgame`/`position`/`go depth\|movetime`/`bestmove`/`quit`），另有非标准的 `perft` 供规则对数。编译方式与测量台一致：`xcrun swiftc`，不经过 Xcode |
| `tools/lib/uci-engine.js` | UCI 子进程封装（发命令、等响应、取 bestmove、收 info）。从 `pk-match.js` 里抽出来共用 |
| `tools/match.js` | **对局台**：A/B 两方可以是 `uci:<路径>` / `js` / `pika`；开局取自项目自带开局库；轮流执先；判将死·困毙·三次重复·60 回合无吃子·手数上限；出胜负与 Elo 差 + 95% 置信区间 |

**用法**：

```bash
./tools/uci/run.sh                                   # 先编出 UCI 前端（-O）

# A/B 自我对局：同一个引擎的两个构建（改前 vs 改后）
node tools/match.js --a uci:tools/uci/build/xq-uci --b uci:/tmp/xq-uci-old --ms 300 --games 40

# 和 Pikafish 比（它固定 100ms，我们 500ms）
node tools/match.js --a uci:tools/uci/build/xq-uci --ms-a 500 --b pika --ms-b 100 --games 8

# 只验规则：两份规则实现 + Pikafish 三方逐节点 perft 对数
node tools/match.js --perft 3
```

**这道台子本身也做了验收**（不能测量已知差的台子是没用的）：

| 验收项 | 结果 |
|---|---|
| 同引擎同设置自对弈 | 2 局 1 胜 1 负 —— 换先手之后对称，符合预期 |
| **能否测出已知的实力差**（6 局，第一批） | A=400ms、B=40ms（**故意造一个 10 倍差距**）：A **4 胜 2 和 0 负**，得分率 83.3%，Elo 差 **+280**，95% 区间 **[+21, +538]**（不含 0） |
| ⚠️ **6 局不够，同一台子会给出相反结论** | 同一个 10 倍差距**重跑第二批 6 局**：A **3 胜 2 和 1 负**（66.7%），+120，区间 **[−135, +376]**（跨 0）→ 结论变成「看不出差别」 |
| ✅ **20 局（可信的那一批）** | A **8 胜 11 和 1 负**，得分率 **67.5%**，Elo 差 **+127**，95% 区间 **[+25, +229]（不含 0）** → 差别是真的、方向正确。**这也就是 10 倍时间差的真实量级 ≈ +130 Elo**（它只换来约 1 层半的深度） |
| 分辨力 | 6 局约 ±200~250 Elo，20 局约 ±107 Elo；提示里会直接写明「本批次能分辨多大差距」，避免把小样本噪声当结论 |

**顺带验掉的一件事：两份规则实现与 Pikafish 完全一致。**
`perft` 从标准开局逐深度对数（本项目 Swift / 本项目 JS / Pikafish）：深度 1 都是 **44**、
深度 2 都是 **1920**、深度 3 都是 **79666**，且深度 3 的 **44 个根着法逐个计数完全相同**。
这条很关键 —— 后面所有「搜索变强了」的结论都建立在「两边规则一致」这个前提上，
现在这个前提是被验证过的，而不是假设的。

**顺带量出来的一个规则缺口**（对应下面 P2）：**和棋判定缺失比预想严重得多。**
20 局自对弈里有 **9 局（45%）** 是**三次重复局面**结束的（28~121 手那种来回走），
另有 2 局撞手数上限。也就是说**一半的对局根本没下出结果，而是被"循环"吃掉的**。
App 里没有任何和棋判定，引擎也不知道自己在走向循环、更不会躲 —— 这是用户一眼能撞上的问题。
（更早的 6 局批次里也有 2 局是这么结束的，两批数据一致。）

**验收期间顺手修掉的两个 bug（都是"静默退化"，不报错但会骗人）**：

| bug | 表现 | 根因 |
|---|---|---|
| 进程内 JS 引擎「不会走棋」了 | `--a uci:… --b js` 时两局都终止于「引擎没有给出着法」，**看着像搜索引擎坏了** | 统一接口时 `playGame` 只传了 `(history, limit)`，进程内适配层还需要 `side` → 拿到 `undefined` → 搜索找不到着法返回 `{move:null, depth:0}`。修法：适配层自己从历史推导 `toMove`，调用处也显式传下去 |
| 全和棋时打出 `95% 区间 [0, 0]` | 4 局全和棋，输出 **`Elo 差 0，区间 [0,0]`** —— 看着像"精确测得差距为 0" | 每局得分都是 0.5 → 样本方差为 0 → 区间宽度算成 0。**这是无信息，不是测出零差距**。已改成单独分支明说「本批不提供任何强弱信息」 |

> 一处**与计划的偏离**：原计划是「改造 `pk-match.js`，让它也能驱动 JS 之外的引擎」。
> 实际做下来发现 `tools/match.js` 已经能覆盖 `pk-match.js` 的全部能力（它本来就只有
> 「Pikafish vs 本项目」一种对局），再造一份「两套驱动逻辑」不划算，所以
> **`pk-match.js` 保持原样不动**，新东西集中在 `match.js`。要跑旧场景时
> `node tools/match.js --a uci:tools/uci/build/xq-uci --b pika` 即可。

> **没有这一步，下面每一条都无法验收。** 这也是本项目一贯的纪律：
> 先能量，再改 —— 9-22 那次特征实验之所以能干净地得出「将位条件无效」，
> 就是因为先写了线性探针。

### P1 — 搜索剪枝：让同一个时间预算搜得更深（收益最大）

目标不是「变强」，是**把开局的节点数降一个数量级**（2833 万 → 300 万量级），
从而让 3.5 秒预算够到第 8~9 层。

| # | 改动 | 为什么先做 | 预期 |
|---|---|---|---|
| 1 | **空着裁剪 null-move** | 象棋开局几乎不存在 zugzwang，条件最有利；一个节点就能砍掉整棵子树 | 节点数常降 2~4 倍 |
| 2 | **着法排序补齐**（见下） | 开局退化的**根因**；空着裁剪和 LMR 的效果都建立在排序好之上 | 决定上面两条能不能兑现 |
| 3 | **后期着法削减 LMR** | 排序好时，靠后的着法用降 1~2 层搜基本安全 | 再降 2~3 倍 |
| 4 | **期望窗口 aspiration** | 现在根节点每轮迭代都从 `-infinite` 重开窗口，浅层浪费严重 | 10~30% |
| 5 | **将军延伸 check extension** | 象棋的将军极其强制，漏一层就是漏杀 | 战术视野，不算节点数 |
| 6 | **静态搜索里也搜将军** | 现在 `quiesce` **只搜吃子**，而象棋的杀往往靠连续将军 | 减少「漏杀」 |
| 7 | **SEE（静态交换评估）** | 现在吃子排序只按「被吃子价值 - 自己价值」，会把「亏本吃」排到前面 | 排序质量 |

**排序退化的具体补法**（对应第 2 条，这是开局那 8.3 倍差距的正面解药）：

- 现在的兜底分数只有**历史启发式**（`history[from*90+to]`），开局拿不到信号。
  补齐标准的四层排序：**TT 着法 → 好/等吃子（SEE）→ 杀手着法 → 历史+静态棋理**。
- 静态棋理的候选（都在现有 `pstXxx` 表之外、可直接算）：
  过河兵推进、车的**机动性**（可走格数）、马腿被别、炮的**炮架**有无、
  是否正在威胁对方大子。这些正好是「开局该展开哪一步」的信息。
- 注意：这不是新增**评估函数**（评估已证非瓶颈），只是新增**排序用的轻量特征**，
  代价必须控制在每着法几十纳秒以内。

#### P1-2 排序补齐（静态棋理 + SEE）⚠️ **做了，但「节点数」的收益换不成棋力（2026-09-23）**

**做出来的东西**（Swift `Search.swift` 与 JS `engine.js` 同步改）：标准四层排序
**TT 着法 → 好/等吃子（SEE ≥ 0，MVV-LVA）→ 杀手着法 → 安静着法（历史 + 位置表增量）**，
亏本吃降到 1M 档、排到所有安静着法之后。

| 改了什么 | 怎么算的 |
|---|---|
| 静态棋理：**位置表增量** `pstDelta` | 走子前后各查一次现有 `pstXxx` 表做差。一张表已经编码了「过河兵推进 / 马往前跳 / 车站好线」，所以**一个差值同时覆盖这几条**，成本只有两次查表。行镜像之后红黑同向，「增量 > 0」对两边都等于「这颗子变好了」，不需要按颜色翻符号 |
| **SEE**（静态交换评估） | `f(n)=G[n]`、`f(k)=G[k]−max(0,f(k+1))`、答案 `f(1)`，`G=[被吃子, 各攻击者…]` |
| **SEE 的两道门** | ① 只对「可能亏」的吃子算（`capVal < attVal`）；吃大子/平换走 MVV-LVA ② **只在 ply ≤ 4 的浅层算**（理由见下） |
| 稳定排序 | Swift 的 `sort` 不稳定、JS 的稳定。加了「平局按原下标」，两端顺序才一致 |

**实测（Apple M1 Pro，Release 档，单线程）**

**1. 正确性先立住**（排序**不许改变搜索结果**，这是硬约束）：

| 检查 | 结果 |
|---|---|
| 3 个固定局面 × 深度 4~7（12 个场景） | 分数与最佳着法**完全相同** |
| `tools/order-fuzz.js`：**150 个随机局面**（随机走 4~60 手）× 深度 5 | 分数与最佳着法**全部相同** |

→ 「SEE 把棋盘改坏了」这条被排除。排序只改速度、不改答案。

**2. 固定深度节点数**（越小越好）——**这项看着非常成功**：

| | 开局 | 中局 | 残局 | 合计 |
|---|---|---|---|---|
| PST + SEE | 77.0% | 90.1% | 46.9% | **71.3%** |
| 仅 PST | 92.0% | 96.4% | 47.3% | 78.6% |
| 仅 SEE | 84.1% | 95.4% | 99.1% | 92.9% |

**3. 固定时间能搜到第几层**（这才是用户实际感受到的东西）——**收益几乎全没了**：

| | 开局 300/1000ms | 中局 300/1000ms | 残局 300/1000ms |
|---|---|---|---|
| 改动前 | 5 / 6 | 6 / 7 | 8 / 9 |
| PST+SEE ／ 仅PST ／ 浅4 | 5 / 6 | 6 / 7 | **9 / 10** |

→ **只有残局多 2 层。开局、中局一层都没多。**
原因：新排序的「每节点开销」把省下来的节点吃掉了。同一个中局局面搜到第 7 层：
节点数只有改动前的 95.1%，**耗时却从 349ms 涨到 400ms（慢 15%）**。

**4. 归因**（把 PST 与 SEE 拆成单独的变体引擎，见 `tools/order-variants-swift.sh`）：

- **残局那 2 层全是 PST 的功劳**（残局节点 47.3%，中局 96.4%、开局 92.0%）。
- **SEE 在任何局面都没多搜到一层**，却让**中局**每千节点/秒从 2684 掉到 2177（慢 19%）——
  中局吃子多、SEE 的射线扫描贵，而那里的节点只省下 5%（MVV-LVA 本来就不差）。

**5. 「平均有效深度」**：3 个固定局面的「整数层」分辨率太粗（两边都是 5 层），
所以在**随机局面**上各测 300ms，取平均、并数「谁搜得更深」

**6. 对局台 A/B（300ms/手）**：整棵树 SEE 版 **0 胜 6 负 1 和**（7 局，方向已明就停了）。
⚠️ **但这个幅度不能直接读成「掉了很多棋力」** —— 上面量出来的真实差距只有 0.07 层，

这正是「先问一句『这个幅度对不对得上』」的价值。

**7. 最终形态的 16 局 A/B**（A=PST+浅4 SEE，B=改动前；8 组独立开局各 2 局、轮流执先）：

> 跑这批时发现并修掉了一个**测量台自身的静默缺陷**：「中炮对屏风马」与「五七炮对屏风马」
> 两条棋谱**前 6 手完全同形**，默认 `--open-plies 6` 截断后两组开局无法区分，
> 确定性引擎走出**逐字节相同的两局**——看着跑满 16 局，实际只有 8 局独立。
> `buildOpenings` 已改为按截断后序列去重 + 数量不足时告警（`tools/match.js`），
> 并加自证断言（去重后仍同形就抛错）。跑对局请用 `--open-plies 8`。

| 项 | 结果 |
|---|---|
| 比分 | **A 3 胜 3 和 10 负**（得分率 28.1%） |
| Elo（A−B） | **−163**，95% 置信区间 **[−334, +8]** |
| 判读 | **区间跨过 0：这批看不出差别**（16 局分辨力约 ±120 Elo） |
| 结束原因 | 将死 11｜200 手上限和棋 3｜**长将判负 2**（全是 A 执红送掉） |

两个补充观察，与前面「每节点开销」的结论自洽：
- **长局（200 手和棋 3 局）里 B 的平均层数反而略高**（9.5/9.0/8.3 vs A 9.1/8.8/8.3）
  —— 与「nps 仍低 11%」一致：长局走到后盘，每节点开销的账就显出来了；
- **2 局长将判负又是 A 送的**（B 平均层数 9.7/10.2，A 只有 6.4/6.1）——
  长将缺口对测量的污染是**结构性的**（优势方主动走进长将循环），不是偶发。

**对局台的最终判读**：方向偏负、但不显著；量出来的真实差距（Δ层 +0.035、nps −11%）
与这个比分在数量级上对得上。**P1-2 没通过棋力验收**的结论不变，且 16 局的置信区间
也说明：**再往下就该去修长将缺口 + 降每节点开销，而不是靠加局数把 P1-2 测成显著。**

**最终采用了什么**：**保留位置表增量，SEE 限制在 ply ≤ 4**（`Engine.seeMaxPly` / `SEE_MAX_PLY`）。
理由：浅 4 层能保住 SEE 大部分节点收益（开局 78.2%，整棵树是 77.0%），却砍掉深层那部分代价；
盘面上它比「仅 PST」节点更少（开局 78.2% vs 92.0%）、nps 相同、对「浅 1 层」也更靠前（5:1）。

**但要说清楚**：收窄 SEE 只**挽回了一部分**（整棵树 14:3 → 浅层 9:5；200 局面复核 14:7），
残余代价来自「位置表增量 + 排序数组」本身的每节点开销（nps 仍低 11%）。
14:7 的符号检验 **p≈0.095，没到显著** —— 诚实结论是：
**残局明确变好（+2 层），开局/中局与改动前基本持平（略偏负、但不显著）**。
它**不构成一步「棋力提升」**；按本文件第五节的验收口径，这一步**没通过**。

**下一步不该继续在排序上加东西，而是先把每节点开销降下来**（这是 P3 的活，但它现在是 P1 的前提）：

- 把 `pstXxx` 从 `[[Int32]]`（嵌套数组）**平铺成 `[Int32]`（90 项）**。
  Swift 里每次 `pstPawn[row]` 都要取一个数组值（引用计数 + 边界检查），
  而 `evaluate` 在**每个叶节点**对**每一颗子**都要查一次 —— 这是与排序无关的纯提速，
  改完排序这套东西才有机会由负转正。
  ⚠️ 做这件事时**必须把对照组的二进制用同一个改动重建**，否则测出来的是
  「新引擎 + 提速」对「旧引擎」，那个数字没有意义。
- 排序数组 `[(Int32, Move, Int)]` 每个节点都要堆分配一次。要省就用复用的临时缓冲，
  别每节点新建（尤其别用 `reserveCapacity` 之后还频繁扩容）。

⚠️ **另外一个前提**：先修掉「搜索内的重复判和」与「对局层长将判负」的不一致（见本节末尾）——
否则下一步的空着裁剪会建立在「引擎以为和棋、裁判判负」的错误评估上。

**踩到的坑**（都值得记住）：

1. **SEE 把将/帅算作攻击者**时，正常吃子会被算成 −60000 级巨亏、被降到所有安静着法之后，
   排序反而比不改还差。将的「回吃」在象棋里经常是非法的（被己子挡住、或落点另有保护），
   SEE 不知道这些 —— 所以 **SEE 里必须把将/帅排除在攻击者之外**。
2. **「固定深度节点数」是个会骗人的指标。** 71.3% 看着是大幅改善，
   固定时间下却只有残局多 2 层。节点数只回答「剪枝好不好」，不回答「同样时间能搜多深」。
3. **测量台自己错了三次**（都写在 `tools/order-fuzz.js` 的注释里，都是静默的）：
   着法表示用错字段（JS 里是 `[from,to]` 数组，不是 `m.from`）拼出**不可见字符** →
   引擎解析失败、一直停在开局 → 伪装成「两份引擎在随机局面上不一致」；
   `go depth N` 不带 movetime 被引擎兜底成 80ms → 「固定深度对分」悄悄变成「比谁快」；
   探针一开始没有自证检查。**教训：任何测量工具都必须能回答「我这次到底测到了几条」。**

**顺带发现的一个真实缺口（新，建议排在 P2 之前）**：

**同一个规则，两处实现，判据不一样：**

| 位置 | 机制 | 判据 |
|---|---|---|
| 搜索（`web/js/engine.js` 的 `repIsDraw`，Swift 同理） | 路径上出现 **2 次**重复局面 → 直接返回 **0 分** | **不看着法性质** |
| 对局层（`adjudicate` → `perpetualChecker`） | 取「倒数第三次出现 → 现在」当循环体，逐手看 `check` | 一方**每一步都在将军** → 该方**判负** |

对不上的后果：优势方在搜索里看到「长将循环 = 0 分（和棋）」，觉得不吃亏，
于是**主动走进长将**；到了对局层却按长将判负。**搜索系统性低估长将风险。**
影响有两层：棋力上白送一局；测量上污染 A/B（本次 7 局里占 2 局，
重跑的 16 局里第 5 局也是）。

**修法（复用现成函数，不要另写一套判据）**：`repIsDraw()` 触发时，
用「上一次出现 `curHash` → 现在」这一段当循环体（2 次重复时这段**正好是一个循环周期**），
交给**同一个** `perpetualChecker(cycle)`；返回 `'r'`/`'b'` 时给长将方 **±绝杀分**而不是 0，
返回 `null`（双方都长将 / 都不长将）才给 0。这样三处实现（Swift 搜索 / JS 搜索 / 裁判）
的判据才真正合一。

⚠️ 注意：搜索内判重复用的是 **2 次**，裁判用 **3 次**，**这个不一致是刻意的**（见 P2-1/P2-2），
**不要顺手统一** —— 要统一的只是「长将怎么给分」这一点。

#### P2-2 搜索内重复局面判和 ✅ **已完成（2026-09-22）**

**为什么 P2-1 不够。** P2-1 修的是对局层 —— 用户**看不到**无限循环了，但引擎自己
并不知道自己在绕圈：它仍然会把「走回旧局面」当成一个普通局面继续算分，于是
**一盘赢棋被自己走成三次重复**，最后只能靠对局层判和，等于白送一局。
这就是「窟窿被兜住了，但没被堵上」。

**做出来的东西**：搜索里带上了走到根局面为止的**着法历史**，回到路径上出现过的
局面一律按 0 分（和棋）算。效果是双向的、而且正是我们想要的：

| 谁 | 表现 |
|---|---|
| **优势方** | 躲开循环（0 分比优势分差），继续找赢棋的路 |
| **劣势方** | 主动去凑循环（0 分比输棋好） |

**实现要点**（重写时别踩）：

1. **判定必须排在置换表探测之前。** 0 分是「相对于这条路径」的结论 —— 同一个局面
   从别的路径搜过来并不等于和棋，当成普通评分存进置换表会污染后续搜索。
   提前返回也天然避免了把 0 写进表里。
2. **路径栈要分「不可逆段」。** 吃子、走兵之后，之前的局面不可能再出现（兵只进不退），
   所以遇到这类着法就把计数表清空。
3. **计数用 Map/字典，不用线性回溯。** 安静残局里一段能有上百手，
   每层往回扫一遍会把搜索拖慢；现在是每个节点一次 O(1) 查表。
4. **搜索按「两次重复」判和，对局层按「三次重复」判和 —— 两处不一致是刻意的。**
   搜索里要防的是「双方都愿意重复」导致的死循环，宁可早判；判早了只会让优势方
   更主动地躲开循环，不会把赢棋判成和棋。
5. **长将仍然不判进搜索。** `Rules.adjudicate` / `XQ.adjudicate` 里的长将判负是对局层
   的事（要按整个循环逐手判断「是否每手都将军」）。搜索里若遇到长将循环，会被
   第 4 条的两次重复提前掐掉 —— 结果可能偏乐观（把「会被判负的循环」当成和棋），
   但代价有限：它只会让**本来就在输**的一方更愿意往循环里走。

> 两批一致的负号方向值得记下来，但按 p 值（胜负 4:10，p≈0.18）**还不足以判定回归**。

**怎么解释这个 null 结果**：这个改动是**双向**的 —— 优势方躲开循环（少丢和棋），
劣势方主动凑循环（多拿和棋）。在双方棋力相当、局面多为均势的自对弈里，
两个方向互相抵消，净效果就测不出来。也就是说：

- ✅ **它是正确性修复**：引擎不再「不知道自己正在走向和棋」。
- ❌ **它不是棋力提升**，别拿它当变强的一步记账。

**一个还没试的对齐方案（记下来，别忘）**：搜索里用的是**两次**重复判和，而对局层是
**三次**。对局层才是裁判 —— 于是引擎可能为一个「裁判根本不会判和」的双次重复
去放弃别的走法。改成跟裁判一致（路径上出现第 3 次才算和）会更自洽，
代价是引擎察觉循环更晚。**要动它必须先跑一轮 A/B**，别凭感觉改。

**接线（缺任何一处都等于没改）**：iOS `GameState`（电脑走子 / 混合对弈 / 提示 /
评估条四处）、网页 `app.js`（同样四处）、对局台 JS 适配器、`tools/uci` 的 `go`。
**起始局面必须一起给** —— 残局 / 杀法 / 名局不是从标准开局摆起来的，
少了 `startFEN` 历史会被按标准开局重放，判出来的「重复」全是假的。

#### 剩一条

| # | 问题 | 现状 | 后果 |
|---|---|---|---|
| 3 | 置换表**始终直接覆盖** | `tt[slot] = te`，无深度优先替换、无老化 | 2^18 个槽位被浅层节点冲掉，深层结论留不住 |

### P3 — 速度：让同一深度更快

| # | 改动 | 依据 |
|---|---|---|
| 1 | **合法着法生成一次到底** | 现在每个节点是 `genMoves`（0.29 µs）之后**逐着 make/unmake + `inCheck` + `kingsFacing`**（0.14 µs/着 → 39 着 = 5.5 µs）。也就是**每个节点 95% 的着法相关开销花在排非法着法上**。改成一次生成真合法着法，或把「被将检测」改成增量维护 |
| 2 | **`quiesce` 用吃子专用生成器** | 现在 `Rules.genMoves` 生成全部 39 个着法再筛出 ~5 个吃子，浪费 8 倍 |
| 3 | **评估增量更新** | `evaluate` 每次全盘扫 90 格（0.24 µs）。这是全项目最热的一个函数，改成走子/回退时增量加减子力与位置分 |
| 4 | 置换表加大 + 深度优先替换 | 2^18 → 2^20/2^21，槽位冲突显著减少（内存代价各 2~8 MB） |

> 顺带说明一个反直觉的读法：**「千节点/秒」不是棋力指标**。
> 这里 2500–3900 knps 看着不低，但 3.5 秒只够 1000 万节点，开局照样到不了 8 层。
> 决定棋力的是**「给定时限内能搜几层」**，也就是「节点数下降速度」×「每秒节点数」。

### P4 — 架构：接 Pikafish（一步到位拿到职业级，但换了赛道）

这条 `docs/engine-strategy.md` 已经论证过，这里只更新两点状态：

- 当时的前提「当前引擎是 JS 写的」**已经过时**：iOS 侧现在是原生 Swift 引擎，
  P4 里「先移植到原生」的那一步**已经做完**（顺带把 P3 的提速空间打开了）。
- **iOS 上不能 fork/exec 子进程**。所以「App 内以独立进程跑 Pikafish」在 iOS 上不成立 ——
  「进程隔离绕开 GPL」这条路只能在**服务器**上走。
- 因此结论不变：**要职业级棋力，就把引擎放服务器，App 走网络**（`engine-strategy.md` 路线二）；
  要**离线可用**，就只能在 P1~P3 里做，天花板是「业余强手」。

**这两条不冲突，也不该混在一起做**：P1~P3 是让「离线的那档」变强，P4 是给「联网的那档」
换个天花板。

### P5 — 评估：只做一小块，其余别碰

评估已实测**不是瓶颈**（网络 ≈ 线性模型，0.53 vs 0.53），所以：

- ❌ 不加数据、不加大网络、不换编码、不加将位条件（四条全都实测过，见「四、不该再做的事」）
- ⚠️ **唯一值得碰的是残局知识**：残局分支少、搜索能到 11 层，但**深度换不来「车兵必胜士象全」
  这类结论性知识**。纯靠搜索会在某些残局里来回走。这一块属于「评估」，但收益点很窄，
  建议等 P1~P3 做完、有对局台能验收之后再决定。

## 四、不该再做的事（全是实测过的否定结论）

| 方向 | 结论 | 证据 |
|---|---|---|
| 堆数据量 | **无效** | 唯一局面 472 万 → 4187 万（8.9 倍），网络相对手写评估的差距没有缩小，配对检验 p=0.55/0.24/0.09 全不显著 |
| 加大网络 | **无效** | 256/32 → 512/64，平均名次无显著变化 |
| 换训练目标 | **无效** | 去掉 sigmoid 压缩后 loss 从 0.65 降到 0.49，判断力没提升 |
| 加将位条件（HalfKA/FullKA） | **无效** | 均势档线性探针 0.5320 → halfka 0.5347 / 随机分桶 0.5305 / fullka 0.5143，净收益 ≈ 0 |
| **把网络接进带搜索的引擎** | **无效** | 单节点成本 570 ns → 37.8 µs（慢 66 倍），同预算少搜 1.2 层，质量却统计并列（丢分 50.1 vs 53.8，p=0.57） |
| 标签噪声 | **不是瓶颈** | 均势档理论上限 0.9985（σ组内 1.91 / σ组间 35.14） |
| 评估容量 | **不是瓶颈** | 网络 0.5363 vs 线性模型 0.5320，只差 0.004 |
| **只看「固定深度节点数」就验收排序** | **会判错** | 节点数 71.3% 看着是大幅改善，固定时间下却只有残局多 2 层、开局/中局一层没多；最终 16 局 A/B 为 3 胜 3 和 10 负、Elo −163 [−334,+8] 跨过 0（P1-2） |
| **整棵树都算 SEE** | **不划算** | 开局节点省 16%，但中局每千节点/秒掉 19%（同一深度耗时 349→400ms）——固定时间下任何局面都没多搜到一层；150 个随机局面 300ms 平均深度 **14:3** 落后于不改 |
| 把将/帅算进 SEE 的攻击者 | **反而更慢** | 将的「回吃」常常非法（被己子挡住 / 落点另有保护），SEE 会把正常吃子算成 −60000 再降到安静着法之后 |
| 用「3 个固定局面的层次」区分排序变体 | **分辨率不够** | 两边都是 5 层 / 6 层，看不出差别。改用几十个真实局面的**平均有效深度**（`tools/order-fuzz.js --mode time`） |

> 一句话：**评估这一侧的能量已经挖完了。剩下的杠杆全在搜索。**

## 五、建议的推进顺序

每一步都以「对局台能量出来的 Elo」验收，没有验收就不进下一步。

| 步 | 内容 | 为什么这个顺序 |
|---|---|---|
| ~~0~~ | ~~P0 对局台（UCI 前端 + A/B 自我对局）~~ **已完成 2026-09-22** | 台子自己也验过：故意造 10 倍时间差能测出 **+127 Elo**（20 局，区间 [+25, +229] 不含 0；6 局那批 ±200 的不算数）。**从这一步往下，每一步都能用 Elo 验收了** |
| ~~1~~ | ~~P2-1 对局层和棋判定（长将/60 回合/三次重复）~~ **已完成 2026-09-22** | 改动最小、风险最低、是用户立刻能撞上的规则缺口，先止血。**长捉刻意留白**（判定做错的代价比不做更糟，理由见 P2-1） |
| ~~2~~ | ~~P2-2 搜索内重复局面判和~~ **已完成 2026-09-22** | 把「对局层兜住的窟窿」真正堵上：引擎自己认得循环 = 和棋，优势时不再白送一局。也是后面剪枝能安全引入的前提 |
| ~~3~~ | ~~P1-2 排序补齐（静态棋理 + SEE）~~ **已完成 2026-09-23**，但**结论是「节点数大幅改善、棋力几乎没动」** | 是开局 8.3 倍差距的**根因**，也是 P1 其余各条的**前提**。实测：固定深度节点数降到 **71.3%**，固定时间却只有**残局多 2 层**（开局/中局一层没多）；SEE 的「每节点开销」在中局把收益吃了回去（慢 19%）。最终**保留位置表增量、SEE 限制在 ply ≤ 4**。详见 P1-2 |
| **4** | P1-1 空着裁剪 | 依赖排序；单条收益通常最大。⚠️ 进这一步之前**先把长将判负接进搜索**（见 P1-2 末尾）—— 否则「重复=和棋」会让空着裁剪白救劣势局 |
| **5** | P1-3/4 LMR + 期望窗口 | 同样依赖排序 |
| **6** | P3-1/2 合法性检查与吃子生成 | 纯提速、不改变搜索结果，风险最低的「稳赚」项 |
| **7** | P1-5/6 将军延伸 + 静态搜索搜将军 | 战术强度；做完 3~6 之后再上（否则节点数会先爆炸） |
| **8** | P3-3 评估增量 + TT 改进 | 收尾优化 |
| **9** | 视验收结果决定：残局知识（P5）还是引擎服务器（P4） | 两条不同赛道，不该在没数据时先定 |

**每步的验收口径**（统一，避免又出现「相关系数 0.865 / 均势档只有 0.53」那种误读）：

1. **固定时间**（不打固定深度 —— 应用里用户就是按时限感受棋力的）
2. **同一组开局**（先手/后手各半，开局手数固定，避免库招影响）
3. **看「平均丢分」而不是「平均名次」**（名次是 0~7 的整数，分辨率不够）
4. 报告**样本数与置信区间**，p 值不显著就老实说「无差别」

### 顺带可修的一项（不涨棋力，但省用户时间）

由 1.2 表直接得来：迭代加深是「整层搜完才认账」，**被掐断的那一层完全白跑**。
所以开局阶段点「大师」要等 6 秒，而那 2.5 秒烧掉的第 8 层结果**根本不会被采用**。

便宜的缓解：**收敛就提前收工** —— 连续两层给出同一最佳着法且分数稳定时提前返回。
代价是放弃「本可以搜更深」的可能（严格说是略降棋力），
所以建议**等 P1 剪枝做完、对局台能量出代价之后再决定**，而不是现在顺手改。
把它记在这里，是为了别把「等 6 秒」和「更强」混为一谈。

## 六、两个引擎要同步改（工程约束）

| 端 | 文件 | 规模 |
|---|---|---|
| iOS | `ios/XiangqiCoach/Engine/{Rules,Search,Notation}.swift` | 1044 行 |
| 网页 | `web/js/engine.js` | 679 行 |

**两端是同一套算法的两份实现**（同样的 `killers` / `hist` / `quiesce` / `negamax` /
`orderMoves`，连 `LEVELS` 表的 depth/time/slack 都一模一样）。

所以**每个搜索改动都要做两遍**。建议流程：

> **在 JS 侧做算法试验田**（改一行刷新就生效、`pk-match.js` 现成可用），
> 验证有效后**再移植到 Swift**，最后用 P0 的对局台在 Swift 侧复验。
> 不要把「网页能搜 9 层了」当成「App 变强了」。

长期看，两端算法重复维护是个持续成本，值得单独排一次「是否统一」的评估 ——
但**现在不是**（P0 还没做，统一了也证明不了结果）。

验收口径（写在脚本输出里，避免又出现「相关系数 0.865、均势档只有 0.53」那种误读）：

所以在里面加实验性的搜索变体不会影响 App 构建。
