# 离线预计算：怎么做、能做到什么程度（2026-09-24）

> 一句话：**把「强引擎」从运行时搬到构建期** —— 用强引擎离线把内容库里每个局面的结论算好、
> 存成数据随 app 发布。app 里没有引擎、没有权重，也没有网络依赖。

## 一、原理与边界（先把「做不到什么」说清）

预计算只能覆盖**你事先枚举出来的局面**。所以它天然是**内容增强**，不是**通用分析**：

| | 能不能覆盖 | 说明 |
|---|---|---|
| 名局 / 教材 / 教程的局面 | ✅ **100% 覆盖** | 内容是有限的，可以逐个算 |
| 杀法题、残局题 | ✅ **100% 覆盖** | 连同「正解 + 完整 PV」一起存 |
| 开局（前 N 手主流变化） | ✅ 覆盖主流线路 | 全展开是组合爆炸（3^16 ≈ 4300 万），只存主流 |
| 自由对弈的开局段 | ⚠️ 部分命中 | 用户越走教材/常见线路，命中率越高 |
| 自由对弈的中后局 | ❌ 覆盖不了 | 用户的棋是无限的 → **退回本地引擎兜底** |

**关键结论：预计算恰好覆盖的正是「教练 app 最核心、最值钱」的那三块内容**（名局复盘、杀法讲解、
残局教学）—— 而自由对弈本来就是本地引擎的活。所以这个方案的契合度比看起来高。

## 二、能做到什么程度

现在 app 的分析深度是 **depth 4 / 450ms**（`web/js/app.js` 的 `analyzeMove`），
评估条是 **depth 3**。预计算之后：

| 能力 | 现在（depth 4 本地） | 预计算之后 |
|---|---|---|
| 「这手是疑问手 / 漏着」 | 靠深度 4 猜，经常判错 | **客观判定**：分数掉了多少，有据可依 |
| 该走哪里 | 只有一个分数 | **完整 PV**：「该走这里，接下来 …」 |
| 胜率 | 模糊 | 每步一个胜率数字 |
| 演示解法 | 做不到 | 杀法题直接**逐步演示正解** |
| 大模型讲解质量 | LLM 拿 depth 4 的结论去编 | LLM 拿**确定结论 + PV** 去讲 → 质量跟着涨 |

最后那条是**低成本的连带收益**：讲解链路不用改，只是喂进去的「事实」变准了。

## 三、数据规模估算（完全放得下）

紧凑**二进制**定长记录，单条约 40~60 字节：

```
key      棋盘串（90 字节，或 4bit/格 压到 45）+ 走子方   ← 项目已有约定：用完整棋盘串，不用哈希
best     最佳着法 from/to 各 1 字节
score    cp，2 字节
pv       0~8 个着法 × 2 字节
meta     depth / 来源标记，2 字节（便于日后知道哪些是旧的）
```

| 内容 | 局面数 | 大小 |
|---|---|---|
| 名局 1000 个 × ~100 手 | 10 万 | ~5 MB |
| 杀法 + 残局 5000 题 × ~10 | 5 万 | ~2.5 MB |
| 开局库（只存主流线路） | 5~20 万 | ~5~10 MB |
| **合计** | **20~35 万** | **约 15~25 MB** |

→ 相比内置引擎的 54 MB（48 MB 权重 + 6 MB 二进制），**又小、又干净**。

## 四、怎么做（工程步骤）

1. **新脚本 `tools/precompute.js`**
   - 输入：局面来源 = `shared/library.json`（名局/杀法/残局）+ 开局库生成器
   - 对每个局面调引擎：`go depth N` 或 `go movetime N`，**`MultiPV=3`**（存前 3 个候选着法，
     这样「这手是好是坏」可以用候选间的分差来判）
   - 输出：二进制分片 + 索引
2. **多进程跑**：对局台已经有 `--jobs` 的现成模式，直接复用思路。
   Windows 那台 8 核 / 16 线程机很适合（跑一晚能算几十万局面）。
   ⚠️ 记得用 **WMI 启动**、走**绝对路径**、**看 CPU 涨**再走人
3. **数据格式**：按 key 排序 + 二分查找（或直接建内存哈希表）。**不要用 JSON 文本**（约 4~5 倍膨胀）
4. **app 侧**：启动时加载索引（几 MB 无压力）→ 查表 → **命中用预计算结论，未命中退本地引擎**
5. **每条记录带上 `engine + depth + 权重哈希`**：以后换引擎重算时，能一眼看出哪些结论是旧的、
   支持增量更新
6. **分片按内容分组**（名局 / 杀法 / 残局 / 开局），按需加载，避免启动变慢

## 五、许可证安全线

- ✅ **数据是「程序的输出」** —— GPL 管的是程序，不管程序的输出；app 里既没有引擎代码，
  也没有权重文件，**不触发任何分发义务**
- ⚠️ **但「用 Pikafish 算数据」这一步本身仍然是「使用」** —— 严格按 NNUE 许可的字面，
  商业使用同样要授权。预计算**解决了分发问题，没解决「商业使用」这件事**
- 🔴 **绝对红线：不要把 `pikafish.nnue` 一起打包**（那就变成分发权重了）

## 六、数据来源的两个选项 —— 这才是有意思的地方

| 来源 | 分析质量 | 许可证 |
|---|---|---|
| **Pikafish** | 最高 | 商业用途要授权（用**远程**或**本地**算都算使用） |
| **自研引擎**（离线跑 depth 12~16） | 低于 Pikafish，但**远高于 app 现在的 depth 4** | ✅ **零风险** —— 自己的代码，不受任何第三方许可约束 |

**所以有一条完全干净的路**：用**自研引擎**做预计算。代价是分析质量不如 Pikafish，
收益是「可上架 + 可商用 + 可离线 + 不用谈授权 + app 体积只涨十几 MB」。

建议的推进顺序：
1. 先用**自研引擎**跑一版预计算（零风险，先看效果值不值）
2. 同时去问 Pikafish 的**商用授权**（远程 / 本地两种形态，反正你迟早要问）
3. 拿到授权后，把预计算的**数据来源换成 Pikafish** 重算一遍 —— 数据结构不用改，
   只换第 1 步的引擎（记录里的 meta 已经带了来源标记）

## 七、和「服务端引擎」的关系

两者**不互斥，且互补**：

| | 离线预计算 | 服务端引擎 |
|---|---|---|
| 覆盖 | 只有事先枚举的局面 | 任意局面 |
| 离线可用 | ✅ | ❌ |
| 延迟 / 成本 | 零 | 每次调用 |
| 法律 | 只算数据，最干净 | 需**远程引擎**授权 |

→ 最实际的做法：**预计算打底（覆盖教材与常见局面，离线可用）+ 服务端兜底（用户随时下的怪棋）**。
