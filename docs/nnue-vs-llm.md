# 训练出来的 NNUE 与 App 里外接的大模型：定位、优劣与分工

> 结论前置：**两者不在同一层，不构成替代关系。** 一个回答「这步好不好」，
> 一个回答「为什么好」。真正的问题不是二选一，而是**各自的角色有没有摆对**。
>
> 本文数据来自实测，非估算。实测日期 2026-09-21。

---

## 一、先看清各自站在哪一层

```
讲解层   大模型（DeepSeek）        点评 / 复盘 / 答疑          ← 不可替代
  ↑ 把引擎的判断当素材
判断层   评估函数                  手写价值表 → NNUE 网络      ← NNUE 换的是这层
  ↑ 每个叶子节点都要问它
搜索层   α-β 剪枝                  算最佳着法                  ← 不变
  ↑
规则层   走子合法性                马腿 / 象眼 / 将军          ← 不变
```

**NNUE 替换的是「评估函数」**——就是那个手写的「车值 9 分、炮 4.5 分」的价值表。
它不会替换搜索、不会替换规则，**更不会替代大模型**。

大模型在讲解层，距离 NNUE 隔着整整两层。

---

## 二、逐功能对比：谁能干什么

| 功能 | 现在谁做 | NNUE 能接手吗 | 说明 |
|---|---|---|---|
| 走子合法性 | 手写规则 | — | 无关 |
| 搜索最佳着法 | 手写 α-β | ❌ | NNUE 只换评估，不换搜索算法 |
| **局面评估** | 手写子力 + 位置表 | ✅ **显著更好** | 这正是训练目标 |
| **胜率条** | 评估分换算 | ✅ **更准** | 引擎判断变准，换算结果自然更准 |
| **下一步提示** | 搜索 + 评估 | ✅ **质量提升** | 同上 |
| 难度档位 | 深度 + 随机扰动 | ✅ 更好 | 低难度档的「故意犯错」会更像人 |
| **中文点评** | 大模型 | ❌ | NNUE 只输出一个概率数字 |
| **复盘报告** | 大模型 | ❌ | 需要组织语言、给改进建议 |
| **答疑对话** | 大模型 | ❌ | 需要理解自然语言提问 |
| 拍照识局 | 大模型（视觉） | ❌ | 完全不同模态 |
| 混合对弈选着 | 大模型挑 | ⚠️ **建议改** | 见第五节 |

**一句话总结**：NNUE 能做的事，全都属于「算得准」；大模型能做的事，
全都属于「说得出」。

## 三、性能与成本：实测对比

### 延迟差了 5~6 个数量级

| | 单次耗时 | 能否实时 |
|---|---|---|
| **NNUE 推理**（纯 numpy，CPU） | **18 微秒** | ✅ 可以每步都调 |
| NNUE（C++ + SIMD + 增量更新） | 亚微秒级 | ✅ 引擎内部每节点都调 |
| **大模型点评**（实测） | **35.3 秒** | ❌ 只能按需调用 |
| 大模型选着（实测） | **8.6 秒** | ❌ 同上 |

> 实测口径：NNUE 是 20000 次前向取平均（batch=1，模拟引擎里的调用方式）；
> 大模型是一次完整调用，含思维链。
>
> 表里的大模型数字是**修好 token 预算之后**的。修复前分别是 60.6 秒和 40.1 秒，
> 而且后者直接失败（正文为空，见下一节）。**预算够不够，能让同一个功能差出
> 4 倍耗时，甚至决定它到底有没有生效。**

这个差距直接划定了**功能边界**：

- **需要实时的**（胜率条随走子更新、提示箭头、AI 走子）→ **必须本地**，只能靠 NNUE/引擎
- **可以等待的**（点评、复盘）→ 联网调模型完全可接受

### 成本结构完全不同

| | NNUE | 大模型 |
|---|---|---|
| 体积 | 1.3 MB | — |
| 运行成本 | **零** | 每次调用都计费 |
| 联网 | 不需要 | 必须 |
| 离线可用 | ✅ | ❌ |
| 一次性投入 | 训练一个白天 | 无 |

### 大模型的实际 token 开销（实测）

| 任务 | 输入 token | 输出 token | 其中思维链 |
|---|---|---|---|
| 点评局面 | 490 | 6916 | **6769（98%）** |
| 混合对弈选着 | — | 5001 | **5001（100%）** |
| 复盘整局（早前实测） | — | 需 8000 预算 | 4855~5284 |

**注意那个 98%**：推理模型的实际输出里，思维链占掉了绝大部分，
真正的正文只有一两百字。这意味着——**大模型的成本和延迟，主要花在"思考"上，
而不是花在"说给你听"上**。这个开销是绕不开的（深度思考正是它有价值的原因），
但要知道钱花在哪。

⚠️ 一个反直觉的点：**`max_tokens` 只是上限，不按它计费**。
所以把预算调大不会多花钱——反而能避免"正文被思维链挤没"导致的**重试**，
而重试才是真花钱的地方。

## 四、大模型路线被低估的成本：不确定性

这一节是实测里最有价值的发现。

### 同一个任务，有时成功有时失败

实测同一个局面下的「混合对弈选着」：

```
输出 token: 5001
其中思维链: 5001      ← 全部
正文      : (空)
结果      : JSON 解析失败，静默回退到引擎首选
```

**正文 0 token，功能等于没跑。**

根因是 token 预算不足（当时设 2500，重试到 5000 仍不够），
而**失败是静默的**——用户看到的是「大模型选着」面板正常显示，
实际走的是引擎首选，**没有任何提示说模型没参与**。

修复后实测（预算提到 10000，重试次数 2 → 3）：

| | 修复前 | 修复后 |
|---|---|---|
| 耗时 | 40.1 秒 | **8.6 秒** |
| 输出 token | 5001（**全是思维链**） | 1532（思维链 1504） |
| 正文 | 空 | `{"move":"炮8进4","reason":"引擎评估最高…"}` |
| 结果 | 解析失败，静默回退 | 选着合法，与引擎首选一致 |

同一个功能、同一个局面，**耗时差 4.7 倍，一个能用一个不能用**。
差别只在预算给够没有。

顺带一个观察：修复后思维链只用了 1504 token，而修复前"想"了 5001 token 还没想完。
**同一个任务的思维链长度波动极大** —— 这也是为什么重试次数要多留一次。

> 但这件事真正的启示不是"改个数字"，而是：
> **大模型这条链路的失败模式是隐蔽的。**
> 它不报错、不崩溃，只会安静地产出空结果，
> 然后代码"聪明地"回退到备用方案 —— 表面上一切正常。
> 如果不是专门测了一次，这个功能会一直带着缺陷上线。

### 和 NNUE 的对比很鲜明

| | NNUE | 大模型 |
|---|---|---|
| 确定性 | **完全确定**：同样输入必然同样输出 | 同样输入可能不同输出 |
| 失败模式 | 要么算得出，要么初始化就报错 | **可能"看起来成功"但实际没生效** |
| 排查难度 | 低（数值可逐步核验） | 高（要盯着 token 用量和 finish_reason） |
| 是否需要联网 | 否 | 是（断网即失效） |

**对「对弈」这种核心功能，确定性很重要。** 这支持一个判断：
**不要让大模型参与决策，只让它参与讲解。**

## 五、一个该改的设计：混合对弈

当前实现（`pickMoveMessages`）：引擎算 5 个合法候选 → 模型从中挑一个 + 说理由。

**问题在于「挑」这一步：**

1. **候选和评分本来就是引擎算的**，模型「挑」并不比引擎更懂
2. 引擎的 `multipv[0]` 就是最优解，模型挑反而可能选次优
3. 模型可能因为「理由好听」而选出更差的着法
4. 每步要等 40 秒，还要承担 JSON 解析失败的风险（实测就失败了）
5. 失败时静默回退——用户以为模型在参与，其实没有

**建议改成：引擎定着法，模型只解释。**

```
改前：引擎给候选 → 模型挑 + 给理由 → 引擎复验合法性
改后：引擎定着法（带难度档随机性）→ 模型解释「这一步为什么好」
```

好处：

- **棋力完全不受模型影响**（引擎说走哪就走哪）
- 输出变成纯文本，不需要 JSON，**解析失败的风险归零**
- 延迟降低（解释比「挑 + JSON」简单）
- 理由和实际走的棋**必然一致**（现在可能不一致——模型挑 A，回退走了 B，但面板还在讲 A）

公平地说，「让模型挑」确实带来一个好处：**对局更有变化，不那么机械**。
但这个好处引擎自己就能提供——难度档位的 `slack` 参数本来就是干这个的。

## 六、被忽略的协同效应：NNUE 好了，大模型也会变准

这一节看代码就能确认。大模型的三个功能的**输入**是什么：

| 功能 | 喂给模型的内容 |
|---|---|
| 点评局面 | 棋盘 + **本地引擎评估分** + **引擎筛选的候选着法（含评分）** |
| 复盘整局 | 棋谱 + **引擎评估变化曲线** |
| 混合对弈 | **引擎算出的候选着法（含评分）** |

**大模型不是在"自己判断棋局"，它是在"翻译引擎的判断"。**

所以存在一条强依赖链：

```
NNUE 让引擎判断更准
    ↓
喂给模型的素材更可靠
    ↓
模型的点评和复盘也更准
```

反过来说：**引擎判断错了，模型会跟着错，而且会为错误找出听起来很合理的理由。**
这比"模型直接说错"更危险——因为它的解释看起来是有依据的。

**这也是当前架构最聪明的地方**：没有让大模型去下棋（它下得很差），
而是让它做自己擅长的事——把引擎的数值判断翻译成人类能懂的话。

## 七、大模型的真实上限在哪

它在象棋场景里的强项和弱项都很清楚：

**强项（NNUE 永远做不到）**
- 用初学者能懂的语言解释「炮架」这种概念
- 把「评估 +236」翻译成「红方稍占优，但左翼有个隐患」
- 根据棋友的具体提问做针对性回答
- 组织一份三段式的复盘报告，并给出可执行的改进建议

**弱项（必须靠引擎兜着）**
- 判断局面优劣——**不准**，所以架构里才把引擎评估喂给它
- 生成合法着法——**不可靠**，所以架构里才限制它"只能从候选中选"
- 长时间稳定输出——**不确定**，见第四节

**所以正确的分工已经很清楚了**：引擎管算，模型管说。

## 八、结论与建议

### 不是替代，是各就各位

| 层 | 谁来干 | 理由 |
|---|---|---|
| 规则 | 手写 | 确定、无歧义、改不动 |
| 搜索 | 手写 α-β | NNUE 不负责搜索 |
| **判断** | **NNUE** | 实时、离线、免费、比手写价值表准得多 |
| **讲解** | **大模型** | 只有它能说人话 |

### 大模型的角色应该收窄

| 该做 | 不该做 |
|---|---|
| 点评局面（把引擎判断翻译成中文） | ❌ 自己判断局面优劣 |
| 复盘整局（结合引擎评分曲线找转折点） | ❌ 自己生成着法 |
| 答疑对话 | ❌ 参与走子决策 |
| 拍照识局（多模态） | — |

### 收益对比（如果两个都留着）

| | 只留大模型 | 只留 NNUE | 两者都有 |
|---|---|---|---|
| 棋力 | 业余（手写评估） | **明显提升** | **明显提升** |
| 胜率条准确度 | 一般 | **准** | **准** |
| 实时性 | ✅ | ✅ | ✅ |
| 会讲棋理 | ✅ | ❌ | ✅ |
| 离线可用 | ❌ | ✅ | 部分（讲解需联网） |
| 运行成本 | 每次调用计费 | **零** | 讲解时才计费 |

**NNUE 让「下棋」这件事变得离线、免费、更准；大模型只在「讲棋」时才需要出场。**
两者加起来，才是完整的教学工具。

## 附：本次实测的环境与口径

| 项 | 值 |
|---|---|
| NNUE | 1260 → 512 → 64 → 1（v2 网络，68 万参数），纯 numpy 前向，batch=1，20000 次取平均 |
| 大模型 | DeepSeek `deepseek-flash`，非流式，含思维链 |
| 测试局面 | 炮二平五 马8进7 马二进三 车9平8 车一平二 后的黑方 |
| 运行机器 | Apple M1 Pro（10 核），Python 3.13 + numpy |
| 复现脚本 | 见本节提交记录中的 `/tmp/llm-latency.js`、`/tmp/retest-pick.js` |

> 网络从 v1 的 256/32 放大到 v2 的 512/64，参数翻倍，但实测只从
> **15.1 微秒慢到 18.4 微秒**（+22%）—— numpy 的每调用固定开销占了大部分，
> 矩阵本身很小。所以放大网络几乎不付推理代价。
>
> ⚠️ NNUE 那 18 微秒是**纯 numpy、无增量更新**的数字。
> 真正接进引擎时（C++ + SIMD + 累加器增量更新）能到亚微秒级 ——
> Pikafish 官方说的「sub-microsecond」就是这个量级。
> **这也是为什么必须先把引擎换成原生语言**：JS 里跑这个，每搜索十万节点
> 光评估就要 2 秒，完全不可用。
